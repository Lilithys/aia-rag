Does it actually answer correctly?

Same question as before, re-measured after a forced pivot: OpenAI credits ran out mid-evaluation, so this run is entirely local (Ollama) — mistral-16k generating, qwen2.5-16k judging via RAGAS's standard metrics (context precision/recall, faithfulness, answer relevancy, answer accuracy) instead of the hand-built judge the first run used. All four of require.md's numeric bars are missed this time, and unlike the first run, that's mostly a real quality gap, not a measurement artifact — traced below to a specific, quantified cause, not hand-waved.

Summary

Real answers, real cost -- both go up when the model is local and small

Faithfulness (72.0%) and Accuracy (25.0%) both fall well short of target, and trace back to one concrete, measured cause: mistral-16k fabricates or mis-copies a cited chunk_id on about half of its answers — not a formatting nitpick, since the same calls often carry a wrong number or a reversed yes/no alongside the bad citation. This isn't a judge artifact: §04 re-scores the first run's gpt-5.4-mini answers with this exact same judge and finds a 13-20 point gap on every generation-dependent metric, while Context Precision (56.7%) and Context Recall (87.7%) — both properties of retrieval, not generation — land within ~1 point of the cloud model. Context Precision still reads far higher than the first run's original 16.1% figure, but that's a metric-definition story, not a quality change (§03). Latency is the other real miss: p90 is 183.7s against a 10s budget, a deliberate, discussed trade-off for running on local compute at zero cost rather than a bug (§02).

02Why this run is local, and what that costs

Not a design choice — OpenAI credits were exhausted partway through the RAGAS integration (a retry of 42 NaN-scored items hit insufficient_quota). Getting a local pipeline actually working took real debugging, not just pointing the client at a different URL.

Bug 1
Ollama's default runtime context window is 4096 tokens regardless of a model's architectural max. This project's real prompts (system prompt + ~10 retrieved chunks + history) commonly run 2-8K tokens, so the default silently truncated input.
Bug 2
The obvious fix -- passing options.num_ctx per request -- is itself silently ignored by Ollama's OpenAI-compatible endpoint (confirmed with a needle-in-haystack test: a fact placed at the start of an 8K-token prompt was recovered without the override and lost with it sent). Fixed with custom Modelfiles baking in num_ctx 16384 instead, which every endpoint respects.
Bug 3
The first model tried, qwen3.5:4b, turned out to be a reasoning model: Ollama returns its chain-of-thought in a hidden field before the real answer, and on real-sized prompts that reasoning sometimes consumed the whole completion budget before reaching the answer -- empty output, on every item of a smoke test. Switched to mistral-16k, which has no "thinking" mode -- also a better fit, since this project already rejected CoT for generation (see the design note).
Architecture
src/generation/providers.py holds both a local and an OpenAI config behind one LLM_PROVIDER switch, since this pivot is a stopgap, not a permanent move -- switching back needs no code changes.

What's left, after all three fixes: correct, valid JSON on every call, but genuinely slow (48-120s per generation call) -- confirmed GPU-resident on this hardware, not a CPU-fallback issue, just the real throughput of a 7B model under JSON-schema-constrained decoding. Accepted and documented as the cost of $0 local inference rather than chased with a smaller/faster model, since the plan is to switch back to OpenAI once credits are available. Full detail in that module's docstring.

03Why Context Precision reads so differently this time

16.1% (first run) vs 56.7% (this run) looks like a huge swing, but retrieval hasn't changed at all -- same Chroma+BGE-M3 index, same top_k=10, same corpus. The difference is entirely in the metric's definition. RAGAS's ContextPrecision is literally Average Precision (confirmed by reading its source): each retrieved chunk gets an LLM relevance verdict against the reference answer, then precision-at-rank is computed at every relevant chunk's position and averaged, weighted toward chunks that rank higher. The first run's hand-built metric was almost certainly a flat relevant-count/10 ratio, which is exactly what you'd expect to land near 16% when most questions have only 1-2 truly relevant chunks in a top_k=10 window (the step-4 finding this project already relies on). Average Precision rewards those same 1-2 relevant chunks for ranking near the top of a similarity-sorted list -- which they usually do, since that's what dense retrieval optimizes for -- so the same underlying retrieval quality reads much higher under a rank-aware formula.

What this does and doesn't mean: 56.7% is still a genuine miss against the 0.70 bar, under the metric require.md now calls for. It also means this number is a property of retrieval + the judge model, not of mistral-16k at all -- context_precision and context_recall would read the same regardless of which model generated the answer. §04 confirms this directly: scored under the identical judge, gpt-5.4-mini's context_precision/recall land within ~1 point of mistral-16k's.

04A same-judge, apples-to-apples comparison

The first run's gpt-5.4-mini answers were still sitting in data/logs/generation.jsonl (PII-redacted, untouched by the pivot -- it's an append-only log). Re-scoring those 76 eligible answers with the exact same RAGAS setup used above (qwen2.5-16k judge, nomic-embed-text embeddings, 900s timeout) costs nothing -- no generation, no OpenAI calls, just re-scoring answers that already exist -- and gives a genuinely apples-to-apples comparison instead of two runs under two different judges.

Context Precision and Context Recall barely move (+0.4pt, +1.3pt) -- direct confirmation of §03's claim that these two metrics are a property of retrieval, not the generator. Faithfulness, Relevancy, and Accuracy all show large, consistent gaps favoring gpt-5.4-mini (+19.7pt, +17.6pt, +13.2pt) -- the same direction and a similar magnitude to what §05's citation-hallucination finding would predict, now confirmed under a judge that has no stake in either model. One more finding worth flagging on its own: even gpt-5.4-mini's Answer Accuracy (38.2%) misses require.md's ≥80% bar by a wide margin under this judge -- a much larger gap than the first run's hand-built rubric reported (68.4%). Since this shows up on both models, it reads as this judge/metric combination being strict rather than a claim about model quality; not chased further here, but worth keeping in mind before treating answer_accuracy absolute values as calibrated against the 80% bar the way Faithfulness's 85% bar appears to be.

05Where the faithfulness and accuracy gap comes from

Not diffuse noise -- one specific, measured, model-capability problem explains most of it. mistral-16k is shown the exact chunk_id string for every retrieved chunk in the prompt (quoted, e.g. "Pay driver civil penalty#1_0::c0000") and asked to copy the ones it used into a JSON field. Checking the model's raw output against the actual retrieved IDs, before the pipeline's own guardrail silently strips anything that doesn't match: 47 of 95 non-refused answers (49.5%) contained at least one citation that matched nothing retrieved -- almost always resulting in zero surviving citations on that answer, even when its text makes a confident, specific factual claim. This is a 7B-model verbatim-string-reproduction weakness, not a retrieval or prompt-design problem -- and it correlates directly with the faithfulness/accuracy misses: the two examples below both have a fabricated citation and a wrong factual claim in the same answer.

"How much is the fine if the order was issued between July 1, 1990 and October 31, 1996?"

Gold answerthe civil fine is $200
Generated"The fine is $500."
Citationsnone survived the guardrail (invalid chunk_id emitted)
RAGASfaithfulness 0.00, accuracy 0.00 -- context_precision 1.00, context_recall 1.00 (the right chunk was retrieved and ranked first; the model still got the number wrong)

"Can I ride with someone else if I'm driving a moped?"

Gold answerNo -- the only passenger who can ride with you on the moped is your supervising driver.
Generated"Yes, you can ride with someone else if you're driving a moped as long as they're 21 years old or older and have a valid driver's license..."
What happenedA direct yes/no reversal, with an invented age qualifier that reads plausibly (it's the real rule for supervising a learner, misapplied here) but isn't what the source says for this question. Citation also didn't survive the guardrail.
The guardrail catches the symptom, not the disease: stripping an unverifiable citation stops a fake source reference from reaching the user, which is the guardrail's actual job -- but the answer text itself still ships with the confident, uncited claim attached, which is exactly what require.md's citation requirement exists to prevent. A stricter response to zero-surviving-citations (fall back to a refusal, or flag the answer as unverified) would close this gap; not implemented yet -- see §10.

The same model weakness shows up as a false refusal too. On "what do I do if I need to cancel a hearing that I requested?" (answerable, and retrieval found the right document), the model wrote a real, substantially-correct answer in its own answer field while separately setting sufficient_context: false in the same JSON object -- an internal inconsistency between the two fields that the pipeline resolves by trusting the boolean and discarding the good answer as a refusal. 5 of 85 answerable questions were refused this way; a stronger model appears less prone to this specific kind of self-contradiction (the first, OpenAI-era run had the same failure mode but attributed it to over-literal interpretation rather than field-level inconsistency -- worth re-checking once this project is back on a larger model).

08Query rewriting: worth it?

Follow-up test (queued earlier, run after step 5 first landed): does condensing multi-turn conversation history into a standalone query (then, gpt-5.4-nano; the rewriter role is now llama3.2-16k, not re-run against it) beat the naive "join every turn + question" construction used everywhere else in this project? Same retriever, same harness (src/chunking/evaluate.py) -- only the query text differs between the two runs.

The gain is entirely concentrated in the 73 questions that actually have conversation history (as expected — rewriting is a no-op without history): recall@5 83.6% → 90.4%, MRR 0.685 → 0.748. At k=10, though, recall barely moves (95.9% → 94.5%, within noise) — most correct chunks were already captured by a 10-wide window either way, so the ceiling effect erases most of the recall benefit at our current top_k. This conclusion is about retrieval-set composition at k=10, not about rewriter quality, so it should hold regardless of which model does the rewriting -- but that's an assumption, not re-verified locally.
Recommendation (unchanged): not clearly worth adding at the current top_k=10 configuration — the recall gain evaporates at that width and the latency cost is real, more so now that generation latency is already 18x over budget. Revisit if top_k is ever reduced toward 5.

09Temperature sensitivity

require.md's cost-sensitivity constraint names three knobs: top_k and reranker (both covered in step 4) and temperature (≥3 settings) -- not yet tested until now. Verified first, not assumed, that the parameter actually takes effect through Ollama's OpenAI-compatible endpoint before spending compute on a sweep: three repeated calls at temperature=0.0 on an identical prompt returned byte-identical output every time; three at 1.3 returned varied phrasing with the same underlying fact. Worth checking every time -- options.num_ctx and think both silently no-op through that same endpoint (§02); this is the one of three tried so far that actually works.

Run on a stratified 15-item subset (not the full 101 -- at 48-120s/call, three full-set passes would take many hours for a sensitivity check), covering answerable/unanswerable, with/without history, and every language_relation value.

Context Precision and Context Recall are identical across all three settings (0.544 / 0.846) -- a sanity check more than a finding: retrieval runs before generation and has no dependency on the temperature used afterward, so this is exactly what a correctly-wired experiment should show. Citation validity drops sharply at temperature=1.3 (0.538 → 0.308) while 0.0 and 0.7 tie exactly -- a clean, mechanistically sensible result: verbatim-copying a long chunk_id string gets harder as sampling randomness increases, the same underlying weakness §05 already identified, now shown to get measurably worse under higher temperature specifically. Faithfulness and answer_relevancy both peak at temperature=0.7 rather than falling monotonically with temperature -- not the "lower is always better" result a factual-QA task might predict. Answer_accuracy is the one metric where 0.0 comes out ahead, but at n=13 RAGAS-scored items per setting this specific difference isn't worth over-reading.
Where this leaves the current config: mistral-16k's Modelfile doesn't set an explicit temperature, so production runs at Ollama's own default (0.8) -- close to the 0.7 tested here, not sitting at either tested extreme. High temperature (1.3) is the one setting with a clear downside (citation validity) and no compensating upside; nothing here motivates moving off the current default.

10Next steps

  1. Decide how to handle zero-surviving-citations answers — right now a stripped citation still ships with its (uncited) answer text attached; on a small local model this happens on ~half of answers. Investigated a "refuse when citations end up empty" fix and rejected it with data: citations_valid=False items score *higher* average accuracy than valid ones (0.299 vs 0.199), and 12/41 have accuracy ≥ 0.5 despite the citation mismatch -- refusing on this signal alone would trade citation hallucination for false refusals on answers that were often already correct. A retry-with-reminder approach (attempt regeneration once with an explicit copy-the-id-exactly instruction, keep whichever attempt validates, never auto-refuse) was designed but deprioritized in favor of the temperature sensitivity analysis above; still open.
  2. Investigate why answer_accuracy reads low for both models (§04) — even gpt-5.4-mini misses the 80% bar under this judge; worth checking whether a different/bigger judge, or a look at individual nv_accuracy verdicts, changes the picture before trusting the absolute number.
  3. Loosen the binary sufficient_context flag — a "partial, with caveats" mode could recover some of the false refusals, including the field-inconsistency case in §05.
  4. Multi-turn diagnosis complete, fix not yet built — retrieval quality *improves* with more conversation turns (context_precision/recall both rise), so query rewriting was correctly not the fix; faithfulness *drops* with more turns instead, consistent with "lost in the middle" attention dilution as retrieved context gets pushed later in the message sequence by growing history, not with prompt length itself (measured flat, ~8.2K tokens, across 0 vs 7+ turns -- retrieved-chunk payload dominates, history is comparatively tiny at the conversation lengths in this test set). History compression/summarization for long conversations was proposed as a next step, not yet tested; also surfaces a test-set quality issue worth a mention -- one item (va-008) has a garbled/corrupted question from the translation pipeline, and another (dmv-017) has a required-document label that doesn't match its conversation topic (cp=cr=0).
  5. Multi-sample the RAGAS judge for the formal evaluation deliverable, given the single-pass nature of both this run and the metric definitions themselves.
